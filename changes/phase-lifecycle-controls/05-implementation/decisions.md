# Implementation Decisions

| Decision | Alternatives considered | Reason | Consequence |
| --- | --- | --- | --- |
| `downstream(P)` follows lifecycle order plus only the `next` transition, and only from P or from a phase reached by such an edge. `downstream(judge)` is `[learn]`. | Follow every transition edge from every reached phase (the plan's literal wording). | AC-001 requires reopening evaluate to leave verify complete, but remediate (a lifecycle successor of evaluate) has `next: verify`, and judge has `on_rejected: intake`. Following all edges would reset the whole lifecycle for any reopen. AC-002 (reopen remediate resets verify) still holds. | Conditional loops (`on_code_change`, `on_blocked`, `on_rejected`, `on_blocking_findings`) never widen a reset. Deviation D2. |
| The reset set is ordered in lifecycle order and excludes phases already pending. | Report pending phases. | AC-003: pending handoffs stay byte-identical. | `nothing to reset` is raised when every candidate is pending. |
| `PhaseReopen` raises `TargetError` for state refusals and `ArgumentError` for bad text; the CLI turns both into exit 1 with the message on stderr. | A new exit code. | Matches the existing refusal convention. | Every refusal names what is wrong and the next step. |
| The session marker refuses `phase reopen`, `change release` and `change discharge` only when the variable is present (even empty); the runner's auto-reopen calls `PhaseReopen` with `source: auto`, which skips the marker check. | Refuse every command inside a marker. | REQ-007 exempts the pre-session auto-reopen. | `env -u SOFT_FOUNDRY_PHASE` defeats it, as the threat model states (guard against accident, not a sandbox). |
| `SOFT_FOUNDRY_PHASE` is also set for panel members (Panel launch env) and for single-phase runs. | Parallel only. | The guard resolves the skill from the marker whenever it is present; setting it everywhere keeps one code path and means a panel member is held to its own phase. | Existing panel and guard tests pass unedited. |
| `check` refuses `implement`, `remediate`, `review` and `judge` in `isolated_phases`, and any phase whose skill's write patterns expand into the APP, TESTS or INFRA globs. | Only the three the specification names. | The plan names remediate too; remediation writes code. | A workflow cannot list a code-writing phase as isolated. |
| `Launch#env` is a frozen hash merged into the child's environment by `Process.spawn(env, ...)`; `inspect` prints variable names. | Pass through arguments or a file. | REQ-012: a value may be a credential. | Values never reach argv, files, output or errors (errors are redacted by value). |
| `--env` values are masked in the soft-foundry process's own command line with `Process.setproctitle` once arguments are parsed. | Leave it. | `ps` shows every user the arguments of the soft-foundry process itself, which REQ-012 forbids. | A window of microseconds before the rewrite remains, and the person's shell history keeps the typed value; both are documented residuals (D6). |
| In a parallel run `{phase}` is expanded for single-phase `--env` too. | Parallel only. | One rule is easier to remember and document; a value with a literal `{phase}` is not expected. | Single runs also accept `--env`. |
| A parallel phase is `pass` when its session exited 0, its gate does not fail, its record could be written, and its handoff is not `blocked`; otherwise `fail`. Exit status: 1 if any session failed to start or exited non-zero or HEAD moved, else 2 if only a gate failed, else 0. | Pass on exit 0 alone. | Mirrors the single run (exit 1 for a session failure, 2 for a gate failure) while not reporting a blocked phase as passing. | `phase <id>: pass|fail` and `parallel: N phases run, M passed, K failed` are stable lines. |
| After a parallel run `current_phase` is the first lifecycle phase that is not complete, stepping over pending phases that are skippable (optional, waived, or track-optional). | Literal first non-complete phase. | A literal reading would leave `current_phase` on `remediate` after evaluate and attack, putting the remediation skill's permissions on a change that has nothing to remediate. | `current_phase` is `review` after evaluate and attack both complete. |
| `warn:` lines of a parallel run go to stderr; `parallel:` and `phase <id>:` lines to stdout. | All stdout. | Existing runs print guard and shell warnings on stderr. | A caller reading only stdout sees results; one reading both sees the warnings. |
| `change release` additionally refuses when any gate fails (stale or otherwise) and when the final judgment's outcome cannot be read as exactly one judgment word from the Outcome section of `14-judgment/final.md`. | Trust the judgment handoff alone. | Plan risk R-3, and the unfilled template lists all four words, so an unreadable outcome must refuse rather than guess. | A release on a branch whose evidence went stale is refused until the work is redone. |
| Release items carried from the judgment keep their own ids with `from: judgment`; given items come first. Discharge adds `discharged_at`, `discharge_commit`, `discharge_note`. `change close` on a released record passes discharged carried ids to the existing judgment discharge as confirmed, labelled `change discharge`. | A second confirm step. | One owed list (REQ-018) and no second prompt. | `--force` skips the open-items check but not the judgment's own confirmation requirement, exactly as before. |
| `ci` passes a released record with open items (prints `released: <slug>: N open item(s): ID, ID` and an advisory), fails a merged one with none open (`run soft-foundry change close <slug>`), and for an unmerged one with none open prints a notice and passes. | Fail every released record with no open items. | The specification speaks of merged changes; failing an unmerged branch would block its own pull request. | Documented in D10. |
| Snapshot rows for non-released records gain `released: false` and `open_items: 0`; overview rows gain the keys only for released records. | Add the keys to every overview row. | Existing tests pin the exact overview row for open records and may not be edited. | The overview carries a top-level `released` count. |
| The released UI section is a `<table>` with `scope` header cells, a `sr-only` caption, and state words (`open`, `discharged <time>`); all record text goes through `el(...{ text })`. | A list. | REQ-025 allows list or table; a table carries the note and state in columns. | Styling reuses existing variables only. |
