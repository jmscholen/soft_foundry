# Implementation Decisions

| Decision | Alternatives considered | Reason | Consequence |
| --- | --- | --- | --- |
| The phase's directory is `06a-code-quality` | Renumber `07` to `15`; append it as `16-code-quality` | Existing records keep their directory names, and the name still sorts between verification and evaluation | One directory name carries a letter |
| Whether a record is asked for the phase is two attributes on the lifecycle entry: `enabled_by` (a key of `.ai/repository.yml`) and `since_rules` | A method that names the `quality` phase in `ChangeRecord` | The rule is data in `.ai/workflow.yml`, where the other applicability rules live, and the next conditional phase needs no code | `ControlPlane::Phase` has two more fields; `ChangeRecord#asked_for?` reads them |
| `change new` writes `rules: 3`; the convergence rules still apply from 2 | Raise `ProcessRules::VERSION` to 3 | Raising it would have made every `rules: 2` record legacy and switched its convergence checks off | `ProcessRules::CURRENT` is what `change new` writes; `VERSION` is unchanged |
| A record that is not asked for the phase and has no directory for it reads as pending | Create the directory in every existing record | Existing records are not rewritten (REQ-012); the gate reports `phase pending` with the reason instead of `handoff present` failing | `ci` and `change status` pass on records made before the phase |
| The applicability by risk and track reuses what exists: `quality` is added to `waivable_by_risk.low` and to the light track's `optional` list | New rules for the phase | Low risk already steps over what it may waive, and the light track already has an optional list | No new mechanism; medium and high stay required because they are not listed |
| A change asks for the phase with `run_phases`, where the gate is off as well as at low risk | A separate key | `run_phases` already means "run this though it would be stepped over" | `skippable?` returns false for a conditional phase named there, when the record is new enough |
| The blocking rule is one gate check, `quality findings classed`, run when the handoff is blocked or complete | Fold it into `findings explained` | It has its own message and its own classes; `findings explained` still applies as in review | A complete handoff carrying a blocking finding fails the check |
| "Remediation as the next step" is the `on_blocking_findings: remediate` transition, as for review | Code that reopens remediation automatically | No code reads `on_blocking_findings` for review either; it is the instruction the skills follow, and remediation's predecessor is implementation | The skill tells the session to set `next: remediate` |
| Onboarding keeps a `quality_gate` value whose `set_by` it did not write | Always recompute; never overwrite once present | A person's choice must survive a rescan, and a scan's own value must follow the repository when its languages change | The scan writes `set_by: soft-foundry (language scan: ...)` and replaces only values that start that way |
| This repository's own profile sets the gate off, by the maintainer | Leave it to the scan (Ruby is detected, so it would be on) | Its changes run on the light track, where the phase is optional, and the test fixtures copy this profile | Tests turn the gate on explicitly |
| The Rails review decisions go into `.ai/rules/rails.md`; the refactor steps go into the remediation skill | Put the maintainer's whole text in the code-quality skill | The skill must name no framework (REQ-013), and the phase may not edit code (REQ-003) | The skill points to the rule files |
