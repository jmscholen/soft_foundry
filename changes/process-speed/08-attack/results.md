## Violations found
Every finding concerns code this change modified, so none is marked `outside_change`. ATK-F1 to ATK-F8 come from the first run and were reproduced here; ATK-F9 and ATK-F10 are new.

- **ATK-F1 (minor in this run, was major; ATTACK-005f; REQ-002, AC-002, AC-004).** `ProcessRules#reopened_rounds` counts a reopen as a round whenever the remediation handoff it reset was `complete`, sealed or not. Take one sealed round followed by a documentation-only reopen. A code fix is refused at the seal. The person then follows the refusal's advice and runs `phase reopen remediate`. The refused remediation was never sealed, but the count is now 2, so sealing round two is refused at the cap. The change parks, and the refusal says "has sealed 2 remediation rounds" when one was sealed. REQ-002 defines a round as one seal of remediation. The failure is safe (a person is asked early), but the count is wrong and the message is false. This run rates it minor because it fails toward a person. Evaluation (EVA-002) reads the conservative count as intended. The disagreement with REQ-002's wording is for review to settle.
- **ATK-F2 (major; ATTACK-008a; THREAT-007, MIT-007).** `rules kept` runs only in the first phase's gate. After deleting `rules:` from metadata.yml once intake is sealed: `phase reopen remediate` at the cap is permitted, `PhaseSeal#remediation_refusal` returns nil (by the code: `rules.applies?` is false), and review and judge report `remediation within cap` as skip. Only a gate of intake fails. `change release` (evaluate_all) and `soft-foundry ci` gate every phase and would surface it. `phase seal`, `phase run` and the per-phase gates would not. The reopen, the seal and the cap checks should read the version from the intake seal as `rules kept` does, rather than from current metadata.
- **ATK-F3 (major; ATTACK-008b; THREAT-007).** The threat's vector is "delete the rules version after `change new` wrote it". Deleting it before the intake seal works: the seal goes through with only the hand-edited-keys note naming `rules`, `rules kept` reports skip, and every new check skips for the life of the record. MIT-007 covers only a deletion after the intake seal. The residual should be stated as it is for THREAT-001. Alternatively the intake seal could refuse when the first commit of the record's metadata.yml (the `change new` commit) declared rules and the metadata being sealed does not.
- **ATK-F4 (minor; ATTACK-002, 002c, 002d; THREAT-002, MIT-002).** `sealed_round_commits` counts from `branch_tip(metadata git.branch)`. Pointing git.branch at another existing branch (main) lowers the count to 0 with no history rewrite, so the reopen refusal at the cap is bypassed and nothing parks. With the redirect committed and review rerun, the review gate passes with three rounds and no decision. End to end the cap still held: the remediation seal refuses once git.branch is restored, and every seal is refused while the redirect stands, because the checked-out branch is not the record's. The impact is a round of work started without a person, plus a gate result that cannot be sealed. MIT-002's claim that the count can only be lowered by rewriting history is not accurate. Counting from HEAD as well (taking the larger) would close it.
- **ATK-F5 (minor; ATTACK-007, ATTACK-016; THREAT-006, MIT-006).** `Gate#outside_change_check` compares the finding's `paths` with the diff as raw strings. `./lib/app.rb`, `lib/app.rb ` (trailing space), `lib//app.rb`, `LIB/app.rb`, the glob `lib/*.rb` and the absolute path of the file all name the modified file and all pass. The check is structural, and naming a wrong path would pass too. Normalising the paths (strip, drop `./`, squeeze slashes, refuse globs, compare case-insensitively on case-insensitive filesystems) would close the accidental and the lazy forms.
- **ATK-F6 (minor; ATTACK-005e; REQ-012, AC-015).** `docs_only_refusal` takes the newest phase_reopenings entry whose `reset` includes remediate. The reset leaves out pending phases. So when the remediation handoff is pending after a documentation-only reopen, the advised `phase reopen remediate` resets only verify, evaluate and attack. The docs_only entry is still the newest that names remediate, and the next seal is refused again. The person has to complete the handoff and reopen a second time. The way out exists, but the refusal's advice does not lead to it in this state.
- **ATK-F7 (minor, as specified; ATTACK-005c; REQ-011).** `ProcessRules.documentation_path?` treats every top-level `.md` as documentation, including AGENTS.md and CLAUDE.md. These are the agent bootstrap contract, and `check` content-scans them as instructions. A documentation-only remediation can change them while verify, evaluate and attack keep their evidence. REQ-011 says this explicitly, so the behaviour is not a defect. It does conflict with the reasoning that keeps `.ai/` out ("instructions, not documentation"). Review or judgment may decide whether the pointer files should be excluded.
- **ATK-F8 (minor; ATTACK-010; specification "Failure behavior").** A remediation cap entry with `rounds: "2"` (a string) and `decision: Accept_Residual` is correctly not accepted. The failure says only that no decision exists for round 3; it does not name the `rounds` or `decision` field as malformed. The specification says such a failure "names the field". The approval check behaves the same way for a mis-cased `decision`.

- **ATK-F9 (major; ATTACK-014; THREAT-008, MIT-008).** MIT-008 says that a risk changed after intake is named by the seal's hand-edited-keys note. `PhaseSeal#hand_edited_metadata_keys` only compares uncommitted metadata.yml with HEAD, so a risk change committed by hand is never named. In the probe, a change sealed at intake with risk high is moved to low in a commit named "tidy". The default waivers then grow from none to discover, threat_model, plan, attack and learn. The next seal prints no note, and `waivers permitted` passes, listing the new defaults as if they were ordinary. Nothing compares the risk with the intake seal, the way `rules kept` does for `rules`. A high-risk change can step over its threat model and attack, and the only safeguard is a reader noticing the detail line. Comparing the declared risk with the intake-sealed metadata would close this, as would at least naming the difference in `waivers permitted`. One option is to fail when the risk was lowered and default waivers apply. Another is to warn and park until a person records it.
- **ATK-F10 (minor; ATTACK-013; THREAT-001, MIT-001, TM-001).** The same gap weakens MIT-001. If the forged must criteria approval is committed by hand before `phase seal specify`, metadata.yml is clean when the seal runs and no note names `human_decisions`. The gate then passes with `must criteria approved` = pass. THREAT-001 is already carried as residual (TM-001), but the mitigation's one visible signal is avoidable with a single commit. The note could compare against the previous seal commit (or the record's last `Record` commit) instead of HEAD. In the fixture the seal reported already_sealed, through the legacy `recorded_commit` fallback for records with no tool seal. That behaviour predates this change and is not counted as a finding.
