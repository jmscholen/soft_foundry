# Implementation Decisions

- **Reused the existing `ci`/pre-commit-hook enforcement point** for the "merged but not closed" check rather than building a GitHub Action or bot. It's the same mechanism that already caught the `maturity-report` staleness bug this session — no new automation surface, no new failure mode to operate.
- **`commit_sha_at_judgment`, not `last_commit_sha`, gates the merge check.** An early phase's commit is just the branch's fork point, which is always an ancestor of the branch's own future — using it would flag every abandoned, early-stage change as "merged." Only judgment (or learning) completing makes "this commit is an ancestor of main" mean something. Kept `last_commit_sha` too, since it's an honest, independently useful, and separately tested accessor — just not the right one for this question.
- **Confirmation is plain text-matching (`CONFIRMED: <id>`), not GitHub-account-aware.** Deliberately did not try to distinguish "a human commented" from "a bot commented" — that's a rabbit hole (bot accounts, CI-posted comments, etc.) that doesn't actually serve the goal. The goal is making the claim *checkable*, not *unforgeable*; who has comment access to the PR is the user's existing access control, not something to reimplement here.
- **`--confirm ID` works with no `gh`/network dependency at all.** The PR-comment path is additive, not required — closing a change with an undischarged item never *needs* GitHub if a human is willing to type the id directly on the command line.
- **`close` does not re-run gate checks.** It only asks "is this merged, and is everything undischarged confirmed." Gate correctness is `soft-foundry gate`/`ci`'s job, already continuously enforced while the change is open.
