# Proposed Rule Changes

Proposals are not self-applied. Each becomes a governance change against `.ai/` that follows the standard lifecycle.

| # | Proposal | Target file | Motivating finding | Draft wording |
| --- | --- | --- | --- | --- |
| 1 | Add a `skipped_phases` field to the change-record schema, validated to carry a rationale for every `optional: true` workflow phase left `pending` at `judge` time. | `.ai/schemas.md` (change-record schema section), `.ai/templates/change/metadata.yml` | `13-review/consolidated.md`'s closing line: "Left for `15-learning`: global optionality has no per-change recorded rationale beyond what a human happens to write in a phase document. A `skipped_phases` field on the change record, validated to carry a rationale, would make this traceable without relying on a reviewer to think to write it down." For `init-command`, that rationale currently exists only in `13-review/consolidated.md`'s prose ("Documentation and observability skip — confirmed deliberate, not a gap") and in `14-judgment/final.md`, not in `metadata.yml` itself. | Add to `changes/<slug>/metadata.yml`'s schema: `skipped_phases: []`, a list of `{phase: <lifecycle id>, rationale: <string>, decided_by: maintainer\|reviewer\|judge, recorded_in: <path>}` entries. `soft-foundry gate <phase>` should fail (not merely warn) when a phase's `effective_predecessor` was an `optional: true` phase left `pending`, unless that phase id appears in `metadata.yml`'s `skipped_phases` with a non-empty `rationale`. This makes today's implicit pattern — "mark it optional in `workflow.yml` and hope someone writes down why in a phase document" — into a schema-checked requirement instead of a convention. |
| 2 | Add a checklist item to the security coding standard for temp-file/lock-file-sibling symlink attacks on any write-to-temp-then-rename (atomic write) code. | `.ai/rules/security.md` | V1 / `ATTACK-004`: the atomic-write primitive guarded the final destination's path components but not `<destination>.soft-foundry-tmp`, the predictable temp sibling it wrote through first — a committed symlink there redirected an arbitrary write outside the intended root, undetected through implementation, four verification runs, and one evaluation run, until attack planted the symlink directly (`08-attack/results.md` V1, "critical"). `lib/soft_foundry/safe_write.rb`'s `O_EXCL\|O_NOFOLLOW` fix is the reference remediation. | Add a bullet to `.ai/rules/security.md`: "Any write-to-temp-then-rename (atomic write) implementation must guard the temporary/intermediate path with the same rigor as the final destination — refuse a pre-existing symlink or non-regular file at the temp/lock/sibling path, and open it with an exclusive, non-following mode (e.g. `O_EXCL\|O_NOFOLLOW` or the platform equivalent) so no window exists between checking and opening it. A predictable temp/lock/backup sibling path is a second attacker-plantable destination, not an implementation detail exempt from the same trust-boundary scrutiny as the file being replaced." |
| 3 | Risk-tier the lifecycle: let a change's already-recorded `risk:` level (`metadata.yml`, currently `low`/`medium`/`high`, already populated — `init-command` recorded `risk: medium`) programmatically narrow which phases are required, instead of relying on ad hoc `optional:` marking discovered and re-discovered mid-change. | `.ai/workflow.yml`, `.ai/maturity.yml` (or a new `.ai/policies/risk-tiers.yml`) | The `document`/`index`/`observe` skip for `init-command` was a maintainer judgment call made mid-change ("disproportionate ceremony" for a single CLI command), encoded reactively by editing `workflow.yml`'s `optional:` flags after the gate had already failed on `13-review`'s predecessor check (`13-review/consolidated.md`'s "Harness fix applied after this review completed"), and that same mechanism needed a second bug fix (`52971d8`) because it had only ever been exercised for one phase (`remediate`) before. A risk tier decided at `intake`/`discover` (before any phase runs) would let the workflow declare which phases are required per tier up front, rather than the maintainer discovering the need to skip phases only after `review`'s gate already failed on them. | Add a `risk_tiers:` block to `.ai/workflow.yml` (or a sibling policy file) mapping `low`/`medium`/`high` to a required-phase subset of the lifecycle, e.g. `low: [intake, discover, specify, plan, implement, verify, review, judge, learn]` with `threat_model`/`evaluate`/`attack`/`document`/`index`/`observe` conditionally required by risk tier and declared surfaces (`metadata.yml`'s existing `surfaces:` block already flags `security`, `observability`, etc.). `soft-foundry change new` or `intake` would set `metadata.yml`'s `risk:`/`surfaces:` early, and the gate's `effective_predecessor` resolution would treat a tier-excluded phase as structurally optional from the start, with the tier and its exclusions recorded automatically rather than hand-edited into `workflow.yml` per change. This does not replace human judgment (a maintainer can still override a tier's default), but it moves the *default* decision earlier and makes it declared policy rather than a mid-change workflow-file edit discovered twice. |
| 4 | Give repository-discovery (or a narrowly-scoped new lane) explicit write permission for self-referential packaged files: `.ai/templates/repository.yml` and the begin/end marker wrapping of `AGENTS.md`/`CLAUDE.md` in this repository. | `.ai/skills/repository-discovery/permissions.yml`, `.ai/README.md` (the "Repository discovery is the only skill permitted to write inside `.ai/`, and only to `repository.yml`" invariant) | Residual risk row 10 (structural governance gap) and `13-review/consolidated.md`'s own recommendation: "amend repository-discovery's `permissions.yml` (or `.ai/README.md`'s stated invariant) to explicitly authorize writing `.ai/templates/repository.yml`... define a narrow write lane for the small set of files that are both packaged content and self-hosted in this repository, so this is not a recurring one-off deviation on every future change." Both writes (`IMPL-001`, `05-implementation/deviations.md` (a) and (b)) were made as documented, review-approved deviations against an explicit `deny_write: ["${CONTROL_PLANE}"]` in implementation's `permissions.yml` — genuine permission-boundary crossings, not unlisted gaps, that will repeat on every future change touching these two files until the permission model has an owner for them. | Add to `.ai/skills/repository-discovery/permissions.yml`'s `write:` list: `".ai/templates/repository.yml"` (the unassessed seed template, sibling to the `.ai/repository.yml` this skill already owns). Amend `.ai/README.md`'s invariant to: "Repository discovery is the only skill permitted to write inside `.ai/`, to `repository.yml` and its unassessed seed template `.ai/templates/repository.yml`, because both are evidence rather than policy." Separately define a narrow, explicitly-scoped write lane (new policy entry or an implementation-skill permission carve-out) for wrapping this repository's own `AGENTS.md`/`CLAUDE.md` in the canonical begin/end markers when a change is self-hosting the packaged content it ships — restricted to marker-line insertion only, not general `AGENTS.md` content edits. |
| 5 | Add a requirement-amendment transition to the workflow for when threat modeling or planning discovers the specification itself needs to change. | `.ai/workflow.yml` (`transitions:` block) | `PLAN-002` (`04-plan/handoff.yml`): "Workflow has no requirement-amendment transition; learning should propose one (gaps were absorbed by planning instead)." Ten threat-model-discovered specification gaps were folded into `04-plan/implementation.md` as design constraints (DC-1..DC-10) rather than looped back through `02-specification`, because no such transition exists — this worked because the gaps were compatible with the locked acceptance criteria, but nothing in the workflow would have caught it if they hadn't been. | Add a transition entry: `threat_model: {next: plan, on_specification_gap: specify}` (or equivalent for `plan`), mirroring the existing `review: {next: judge, on_blocking_findings: remediate}` pattern already in `.ai/workflow.yml`. A `threat_model` or `plan` handoff that records a finding tagged as a specification gap (severity `major` or above, or an explicit `spec_gap: true` marker on the finding) routes back to `specify` for an explicit amendment and re-lock of acceptance criteria, rather than being silently absorbed downstream or requiring the full `REJECTED → intake` restart for what may be a narrow, compatible gap. |
| 6 | Require `check`-level detection to default to flagging, not silently permitting, a control-plane-affecting override file (like `repository.yml`) that narrows a *required* detection group's matched-file count to zero, independent of whether the untouched default also matches zero. | `.ai/rules/security.md` (or a new `.ai/policies/override-integrity.yml`) | `ATTACK-F-N01` / `REM-006`: "`repository.yml` overrides are user state that can weaken gate semantics; protected groups now enforced, learning should consider signing or reviewing overrides" — the specific code gap (`Check#check_path_groups`'s `!defaults.empty?` condition) is proposed above as a deterministic check and a follow-up code change, but the *general* principle — a user-writable override file that is consulted for a security- or staleness-relevant detection decision should never be able to silently produce "detection successfully finds nothing to check" as an indistinguishable outcome from "there is genuinely nothing here" — is a rule-level statement, not just a bug fix specific to this repository's `paths.yml` groups. | Add to `.ai/rules/security.md`: "A user- or target-writable override/configuration file that narrows the scope of a required security or staleness check must not be able to produce 'nothing to check' silently. When an override causes a required detection group to match zero files, the tool must flag or fail rather than proceed as if the check passed, regardless of what the unmodified default would have matched." |
