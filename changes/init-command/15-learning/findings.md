# Learning

Change: `init-command` — `soft-foundry init` installs the control plane into an existing repository.
Judged commit: `6bd80f6c419e0a877366a37447f85dc71dd86a30` (`APPROVED_WITH_RESIDUAL_RISK`). This learning phase itself runs at HEAD `09c51a91e43abf4c03184a6e0723cd96c6eb8f3b`.

## What this change taught us

**1. Self-hosting a lifecycle harness inside the repository it governs has a real, recurring cost, not just a theoretical one.** `soft-foundry` is a gem whose own `lib/`, `exe/`, and `.ai/` are simultaneously (a) the product under change, (b) the harness enforcing the lifecycle for this very change, and (c) the packaged source `init` distributes to every other repository. That triple role produced concrete friction:

- Two harness-code bugs in the gate's predecessor logic were found and fixed *while the change that would eventually depend on the fix was in flight*: first `35ceb57` ("Model remediation as an optional loop phase after implementation" — "The gate's predecessor rule was linear, so a completed remediation failed once the phase it repaired was re-run and nothing was blocked"), then `52971d8` ("Fix optional-phase skipping to step back in lifecycle order" — "Skipping a pending optional phase followed its `after:` link, which would have let `document` close with only implementation complete"). The second bug is the *same class* of defect (predecessor/optionality resolution) rediscovered days later against a different set of optional phases (`document`/`index`/`observe` instead of `remediate`), because the first fix was scoped to the one optional phase that existed at the time rather than to optionality as a general mechanism.
- Both harness fixes touched `lib/` (`${APP}`), so both triggered this project's own `stale_evidence_on_code_change` rule against the very change being processed. `35ceb57`'s commit message states this explicitly: "Verification and evaluation evidence at c29509c archived under previous/ and reset for rerun, since harness code shares this repo." Verification ran four times total (three superseded runs archived under `06-verification/previous/`) and evaluation ran four times total (three archived under `07-evaluation/previous/`) over the life of this change — not because the product kept regressing, but because the tool measuring it kept changing underneath it.
- By contrast, the *third* harness change (`6bd80f6`, marking `document`/`index`/`observe` `optional: true`) touched only `.ai/workflow.yml`, and its own commit message and `13-review/consolidated.md`'s "Harness fix applied after this review completed" section both note this is "a `${CONTROL_PLANE}` data change only, touches no file under `${APP}`, `${TESTS}`, or `${INFRA}`, and therefore does not invalidate this review's commit-bound evidence." The lesson generalizes: whether a mid-change harness fix forces re-verification is entirely a function of which path group it lands in, which argues for keeping gate/control-plane *logic* out of `${APP}` where practical, or for being deliberate about which harness surfaces are allowed to change without a full evidence reset.
- A model switch also happened mid-change (commits up through `147fca6` are co-authored `Claude Fable 5.1`; `a7b9df1` onward, starting with the fourth verification run, are co-authored `Claude Sonnet 5`). A model cannot be changed by instruction inside a running agent; switching model required stopping and respawning the affected agents rather than redirecting an in-flight one. This is a harness/session-management fact worth carrying forward explicitly rather than rediscovering per change: a `resolved_model` recorded in a phase's `handoff.yml` is fixed for that phase's *entire run*, and a model-policy change mid-lifecycle is a stop-and-restart event, not a live parameter.
- The maintainer's own scope call — skip `document`/`index`/`observe` as "disproportionate ceremony" for a single CLI command already covered by a README section (per `13-review/consolidated.md`'s deviation-(c) ruling and "Documentation and observability skip" section) — is itself evidence that running all sixteen phases unconditionally has a cost the maintainer had to actively manage mid-change rather than one the workflow decided up front. The mechanism used to encode that decision (`optional: true` in `.ai/workflow.yml`, discovered to need a second bug fix to work for phases other than `remediate`) arrived *after* the decision was made, not before — see the risk-tiering proposal below.

**2. Attack found what verification and evaluation missed, and that is evidence the phase separation is doing its job — but only after the fact, not as a design guarantee.** The critical finding of this change, V1 (`ATTACK-004`, "`<path>.soft-foundry-tmp` symlink"), was a full filesystem-escape: the atomic-write primitive opened a predictable temp sibling (`<destination>.soft-foundry-tmp`) with a following `File.binwrite`, and `guard_path!` checked only the final destination's path components, never the sibling. A committed symlink at that sibling let `init` overwrite an arbitrary file outside the target root while reporting `exit 0`, `check: ok`. This survived:
   - Threat modeling: THREAT-001 and MIT-001 both anticipated the *general* class ("Never open a destination with a following `File.write`... write to a temporary file in the same directory and `File.rename` over the destination, which replaces rather than follows a link") but never named the temp file's own path as a second, independently-attackable destination. The guard that got built covered the thing MIT-001's prose emphasized (the final destination) and missed the thing its own prescribed *mechanism* introduced (the temp sibling).
   - Four verification runs before remediation and one evaluation run before remediation — because verification exercises requirements/acceptance-criteria conformance and evaluation exercises legitimate-and-adversarial-adjacent user journeys; neither phase's persona plants a symlink at an internal implementation detail like a temp-write sibling. That is a deliberate, correct division of labor (`.ai/rules/README.md`: "Rules define what acceptable engineering work looks like... Skills define who performs a responsibility"), not a failure by those phases to do their job — but it does mean the *only* phase in this lifecycle whose explicit mandate is "try to break the write-safety guarantees" is attack, and for this change, attack is what found the change's one critical, unremediated-until-found defect.
   - This raises a genuine question this project has not yet answered, rather than one findings.md should answer unilaterally: should verification or review *also* be required to probe for the specific, well-known bug class "temp-file/lock-file/sibling-of-an-atomic-write path is symlink-attackable," given how narrow and mechanical that check is, rather than relying solely on a dedicated attack phase to catch it? A targeted deterministic check (see below) can close most of this gap cheaply without duplicating the rest of attack's mandate. See `proposed-evals.md` for a harness eval that tests whether verification/review actually catches an injected instance of this bug class, so the answer is measured rather than assumed.

**3. A "safe-direction" fix for a security misclassification can create a new, unrelated correctness defect — the clean-install classification trap.** V5 (`ATTACK-015`) was a real misclassification bug: several target-side conditions (a plain file at `.soft-foundry`, an unwritable directory, a directory where the manifest should be) were incorrectly reported as Soft Foundry-side (`exit 4`, upstream-guidance) instead of target-side (`exit 1`). The fix broadened `Installer#plan.clean` to require *the entire plan* — not just `.ai/`-scoped actions — to be free of `conflict`/`updated`/`forced` before a check failure can be classified upstream. That fix is safe with respect to the original bug (it can only *under*-report a genuine Soft Foundry defect as target-side, never falsely accuse the user's repository), which is exactly why review and judgment both ruled it acceptable residual risk (ATTACK-F-N02). But it is also a strict overcorrection: `NEW-004-clean-install-classification.log` shows that a target repository with nothing more unusual than a *pre-existing ordinary `.gitignore` or `AGENTS.md`* — the common case for any repository adopting Soft Foundry after already existing, not an edge case — permanently makes `clean` false and routes every subsequent genuine internal defect to the wrong (target-side) branch. The general, reusable lesson: when a security-classification bug is fixed by widening a predicate to "the whole plan" or "the whole request" rather than to the specific surface the security property actually depends on, verify or attack the *broadened* scope specifically — the fix itself is now a new source of behavior worth testing, and "fails in the safe direction" is a necessary but not sufficient reason to treat it as low-risk if it also silently degrades an unrelated, load-bearing correctness property (here, REQ-011's upstream-vs-target failure attribution).

## Reviewer/evaluator/attack findings worth generalizing

- **The temp-sibling / lockfile-sibling symlink class (V1, `ATTACK-004`).** Any write-to-temp-then-rename primitive introduces a second path — the temp file itself — that must receive the *same* guard rigor as the final destination: refuse a pre-existing symlink or file at the temp path, and open it with `O_EXCL|O_NOFOLLOW` (or the platform equivalent) so the guard-then-open sequence has no TOCTOU window. `lib/soft_foundry/safe_write.rb` now does exactly this and is a good positive reference implementation. This generalizes past this repository: lock files, `.lock`/`.tmp`/`.bak` siblings, and any "atomic" write pattern in any codebase has the identical shape and the identical risk if the sibling path is predictable and unguarded.
- **The clean-install classification trap (`ATTACK-F-N02`, `NEW-004`).** A boolean "is this operation clean/safe/trusted" flag that is computed over a *broader* scope than the specific property it gates should be treated with suspicion proportional to how common the broadening condition is in real usage — not proportional to how rare it seems in the empty/ideal case the classifier was designed against.
- **`repository.yml` as unreviewed, override-capable user state (`ATTACK-F-N01`, `REM-006`).** A target repository's own control-plane override file can silently narrow detection scope (here, redirect `APP`/`TESTS`/`INFRA` to nothing) for the specific, common case the override-detection logic wasn't built to distinguish from "this repository genuinely has no code yet." `CONTROL_PLANE`/`HARNESS_EVALS` are unconditionally protected regardless, which is why this was scored medium rather than critical — but any future path-group-driven detection has the identical shape of risk if the override file is user-writable and consulted for staleness/permission decisions.
- **Threat modeling's own recorded specification gaps predicted two of the residual risks precisely.** `03-threat-model/mitigations.md` gap 6 flagged `--root` resolution semantics as underspecified before implementation began; MIT-008 (the `--allow-non-git` branch's missing `File.realpath` call) is still open at judgment, carried unchanged from threat model through four verification runs, two attack passes, and review. Gap 7 flagged "clean" needing a precise definition before implementation began; the definition that got built is exactly the one ATTACK-F-N02 later found too broad. When threat modeling names a specification gap as "planning must decide" or "needs to be defined," that gap deserves an explicit, written resolution in the plan or specification before implementation, not just an implicit resolution embedded in code that downstream phases have to reverse-engineer.
- **`PLAN-002`: "Workflow has no requirement-amendment transition; learning should propose one (gaps were absorbed by planning instead)."** Ten threat-model-discovered specification gaps (DC-1..DC-10) were folded into the plan as design constraints rather than looped back through a requirements-amendment step, because no such transition exists in `.ai/workflow.yml`. This worked here because the gaps were compatible with the locked acceptance criteria, but the workflow currently has no *named* path for "threat modeling or planning discovers the specification itself needs to change" other than silently absorbing it downstream or the heavier `REJECTED → intake` restart.

## Proposed deterministic checks

- A static/dynamic check (candidate: extend `soft-foundry check`, or a dedicated test helper) that flags any write path in `lib/` matching a temp-then-rename pattern (a literal or interpolated suffix like `.tmp`, `.soft-foundry-tmp`, `.lock`, `.bak` appended to a destination path) that is not routed through `SafeWrite` or an equivalent guarded primitive. This turns "does every atomic write guard its own temp sibling" from a code-review judgment call into a grep-able invariant.
- A `check` rule that flags a `repository.yml` `paths:` override for any *required* path group (`APP`, `TESTS`, `INFRA`, and not just `CONTROL_PLANE`/`HARNESS_EVALS`, which are already unconditionally protected) whenever the override's glob set matches zero files, regardless of whether the untouched default also matches zero files — closing `ATTACK-F-N01`'s specific gap in `Check#check_path_groups`'s current `!defaults.empty?` condition.
- A gate-level check (see `proposed-evals.md`) that a change record's `metadata.yml` declares a `skipped_phases` rationale for every workflow phase left `pending` at `judge` time whose `optional: true` flag allowed it to be skipped — so "why was this phase skipped" is machine-checkable, not just discoverable by reading a review's prose.

## Proposed rule changes
See `proposed-rules.md` for the full table with target files, motivating findings, and draft wording. Summary: (1) a `skipped_phases` field on the change-record schema with a required rationale; (2) a security-rule checklist item for temp-file/lock-file-sibling symlink attacks on any write-to-temp-then-rename code; (3) risk-tiering the lifecycle so a change's already-recorded `risk:` level can programmatically narrow required phases instead of relying on ad hoc mid-change `optional:` marking; (4) a governance amendment giving repository-discovery an explicit write lane for self-referential packaged files (`.ai/templates/repository.yml`, `AGENTS.md`/`CLAUDE.md` markers), per the residual risk row and `13-review/consolidated.md`'s own recommendation; (5) a requirement-amendment workflow transition, per `PLAN-002`; (6) a stricter default for control-plane-affecting override files like `repository.yml` when they narrow a required detection group to zero matches.
