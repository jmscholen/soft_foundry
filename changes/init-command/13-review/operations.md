# Operations Review

## Scope reviewed
Exit-code contract, failure classification, diagnosability, idempotence, and code-level observability (`.ai/rules/observability.md`) for `init`, `doctor`, `check`, and the CI surface. The `12-observability` lifecycle phase itself is `pending`, addressed separately below rather than treated as a gap.

## Exit-code and classification contract
- `init` returns 0 (success, including a clean no-op re-run), 3 (conflicts remain, nothing overwritten), or 4 (`InternalError`, Soft-Foundry-side defect) from `CLI#init`'s own return/raise paths, and 1 for any other `StandardError`/`TargetError` via `CLI#run`'s outer rescue. `doctor` returns 0/2; `check` returns 0/2; `gate`/`ci` return 0/2. This matches REQ-012's locked statement exactly (0 success, 1 usage/environment error, 3 conflicts remain, 4 Soft-Foundry-side failure) and was independently re-derived from the `EXIT_*` constants and every `return`/exception path in `cli.rb`, not copied from `02-specification/requirements.yml`'s restatement.
- The `InternalError` vs `TargetError` classification boundary — the one place this contract can fail silently — is `Installer#write`'s `rescue SystemCallError, IOError` (wrapped as `TargetError`, i.e. treated as target-side) versus `CLI#init`'s outer `rescue StandardError => e; raise InternalError.new(...)` (anything else, treated as Soft-Foundry-side). This means a filesystem-level failure (permission denied, disk full, path too long) is always classified target-side even if its root cause is a Soft Foundry defect (e.g. a bug that computes a bad path), while a Ruby-level exception (NoMethodError, ArgumentError) from anywhere in the installer is classified upstream. This is a defensible default (a filesystem error is almost always about the target environment) and is exercised by `test_missing_packaged_workflow_is_internal_error_exit_4_with_upstream_guidance` and reconfirmed live in `06-verification` check 9 case (h). See `security.md` for the `plan.clean` scoping issue (ATTACK-F-N02) that separately affects when the *post-install check's own* failures are classified target- vs Soft-Foundry-side.

## Idempotence and recoverability
- A second `init` run on an unchanged target reports every file `skipped` and writes nothing (REQ-005, AC-003) — confirmed by code (`entry_action`'s `existing == entry.bytes` short-circuit before any write) and independently reconfirmed live in `06-verification` check 9 ("all 171 lines skipped"). This satisfies general.md's "prefer... idempotent operations where retries or repeated execution are possible."
- `Installer#apply` plans everything before writing anything (REQ-010) and writes the manifest last, so a mid-run failure leaves a diagnosable, re-runnable partial state; `Installer#write`'s rescue reports exactly which files were already written and whether the manifest was written, in every failure message. This is a concrete, code-level "detection path" for the "partial install" failure mode, satisfying general.md's "a new production failure mode is incomplete unless there is a practical way to detect it."
- The `.soft-foundry/init.lock` `flock` (`Installer#with_lock`) prevents two concurrent `init` runs from interleaving writes; a second concurrent run fails fast with a named, actionable message ("another soft-foundry init is running") rather than corrupting state. Confirmed by reading `with_lock` and cross-checked against `08-attack`'s ATTACK-017 (concurrent inits, denied, inferred from unchanged code plus the passing regression suite — a reasonable inference given `with_lock` was not touched by remediation).

## `doctor`/`check`/`ci` as the operational surface
- `doctor` gives a maintainer a single command to see bootstrap state (git repo, `AGENTS.md`, `.ai/README.md`, workflow/paths present, control-plane check clean, manifest present, pre-commit hook installed, local runtime present) with a binary pass/fail per line and exit 0/2. This is the practical detection path for "is this repository correctly bootstrapped," independent of any external dashboard.
- `check`/`ci` lint the control plane itself and every change record's gates, giving a deterministic, scriptable "is everything internally consistent" signal usable in CI (`.github/workflows/ci.yml` — not modified by this change, but consumes `soft-foundry ci`).
- On this repository specifically, `doctor` currently reports `.ai/manifest.yml` and "local runtime" missing (exit 2) because self-install was deliberately not performed by implementation (`05-implementation/decisions.md`) — a disclosed, expected state, not a defect in this change; it reflects the repository's current bootstrap state, not a bug in `doctor`'s logic (confirmed by re-reading `doctor`'s check list — it correctly reports what is and is not present).

## Observability (code-level, `.ai/rules/observability.md`)
- New material failure modes have a practical detection path: filesystem write failures (`Installer#write`'s rescue), a broken package (`InternalError` with diagnostic and upstream guidance), post-install control-plane drift (`Check` run immediately after `apply`, printed as `check: ok`/`check: failed`), and provider-discovery failures (per-provider `error` field in `runtime.yml`, printed by `onboard`/`init`/`models`) are all surfaced to the operator at the CLI boundary — satisfying "new material failure modes must have a practical detection path" without requiring a deployed-service dashboard.
- No credentials or sensitive payloads are logged: `Provider.sanitize` and `CLI#sanitize` actively strip/bound provider responses and diagnostic text before they reach any output stream (see `security.md`); `runtime.yml` stores only `configured`/`models`/`error`, never the API key itself (confirmed by reading `Onboarding#write_runtime`'s payload construction — `env[api_key_env]` is read only to decide `configured`, never placed in `payload`).
- "Background and asynchronous work must expose failure and retry exhaustion" — not applicable; `init`/`onboard` are synchronous, single-invocation commands with no background or async work.
- "External dependencies should expose latency/error signals when operationally important" — `Provider#discover`'s HTTP calls have explicit timeouts (`read_timeout: 10, open_timeout: 5`) and their outcome (configured/error/model count) is always printed; there is no latency metric, but for a one-shot CLI discovery call (not a running service) this is proportionate, not a gap.

## Why `10-user-documentation`, `11-faq-index`, and `12-observability` are `pending` and not treated as missing work
Per the coordinating instructions for this review and independently confirmed by reading `.ai/repository.yml`'s `observability.*` capabilities (all four `NOT_APPLICABLE`, "No production service; the CLI fails loudly with a non-zero exit code") and `.ai/README.md`'s statement that "Observability assessment is capability-based... A production service must provide failure detection, health signals, operational visibility, and alerting": `soft-foundry` is a locally-invoked CLI tool with no deployed service, so the `12-observability` lifecycle phase (dashboards, alarms, runbooks for a running service) has no applicable subject matter here — it is correctly left `pending` rather than force-fit with placeholder infrastructure that would not reflect anything real. The template scaffolds under `12-observability/` (`alarms.md`, `dashboard.md`, `metrics.md`, `runbook.md`, `signals.md`) exist as empty phase-record placeholders from `change new`, not as evidence of incomplete work.

`10-user-documentation` and `11-faq-index` are pending by the same deliberate-scope-decision logic recorded in `05-implementation/deviations.md` and reconfirmed by every downstream phase (`VER-007`, `EVAL-F-006`): no skill's write set currently covers `README.md`, and product-documentation was judged (by the maintainer, not by review) disproportionate ceremony for a single CLI command already covered by a README section. Review's job is not to re-litigate that scope decision but to record it accurately; see `consolidated.md` for the explicit ruling that this is "accepted, superseded by explicit scope decision," not an open deviation.
