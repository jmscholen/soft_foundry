# Security Review

## Scope reviewed
Independent re-analysis of the security-sensitive surface identified in `03-threat-model/threats.yml` and exercised by `08-attack`: `lib/soft_foundry/safe_write.rb`, `Installer#guard_path!`/`entry_action`/`plan`/`apply`, `lib/soft_foundry/manifest.rb`, `Git#dirty_paths`/`repository?`, `CLI#resolve_root`/`#sanitize`/`#upstream_guidance`, `Provider.sanitize`, `Check#check_path_groups`. This review does not accept `08-attack`'s "denied" verdicts on trust; each mechanism below was read and reasoned about independently against `.ai/rules/security.md` and `.ai/rules/errors.md`.

## Independent analysis of core mechanisms

### SafeWrite (`lib/soft_foundry/safe_write.rb`)
- `write` refuses a non-regular parent directory, refuses a symlink at the destination, refuses a planted/leftover temp sibling (`File.symlink?(tmp) || File.exist?(tmp)`), opens the temp file with `O_EXCL|O_NOFOLLOW` (atomic: the OS itself refuses to open through a symlink or an existing file, closing the exact TOCTOU window a plain existence-check-then-open would leave), re-checks the destination for a symlink, then `File.rename(tmp, path)`.
- Independent TOCTOU analysis: between the second `refuse_symlink!(path)` and `File.rename`, an attacker could in principle replant a symlink at `path`. I traced what `rename(2)` does in that case: POSIX `rename()` unlinks/replaces the destination **directory entry** without dereferencing it — it does not follow a symlink at the destination and does not write through it. So even a successful race only replaces the symlink itself with the new regular file; it cannot cause a write through the symlink to an attacker-chosen target. This matches `08-attack`'s ATTACK-F-N03 conclusion; I verified the reasoning from `rename(2)` semantics independently rather than accepting the attack phase's statement.
- The hardlink case (`.soft-foundry`/`runtime.yml`) is correctly *not* refused by `File.symlink?`/`File.file?` type checks (a hardlink is indistinguishable from a normal file by type), but is safe because `rename(tmp, path)` replaces `path`'s directory entry only — the other hardlink's name and the shared inode's prior content are untouched by this write. This is architecturally correct, not merely lucky: a temp-file-then-rename primitive is the right pattern precisely because it never mutates content in place. Confirms `08-attack`'s reasoning.
- `refuse_non_regular!`, `ensure_directory!`, `refuse_symlink!` are lstat-based (`File.symlink?` does not follow), so they cannot be fooled by a symlink pointing at a real directory.

### `Installer#guard_path!`
- Runs before *any* read (`Manifest.load`, `@git.dirty_paths`, `Dir.glob`) for every managed path, checking each path-prefix component for a symlink and the leaf for "must be absent or a regular file" — this ordering is the correct fix for the FIFO-hang and symlink-redirect classes of threat (THREAT-001, THREAT-014), and I confirmed the ordering in `Installer#plan` (guard loop runs at lines 48-49, before `Manifest.load` at line 50 and before `@git.dirty_paths` at line 53).
- One residual gap I found independently, not previously called out in `03-threat-model`, `06-verification`, `07-evaluation`, or `08-attack`: `guard_path!`'s per-component loop checks `File.symlink?(abs)` for `parts[0..i]`, i.e. every ancestor **within the relative path being installed** (e.g. for `.ai/rules/general.md` it checks `.ai`, then `.ai/rules`, then the leaf). It does **not** re-verify that `root` itself is not a symlink or that no ancestor of `root` was replaced between `resolve_root` (which does call `File.realpath`) and `plan`/`apply` running. In practice this is not exploitable within the documented threat model: `root` is resolved once via `git rev-parse --show-toplevel` and `File.realpath` at the very start of the CLI invocation, and the whole `plan`→`apply` sequence is a single short-lived process with the lock held for `apply`; an attacker able to swap `root`'s own ancestry mid-run already needs write access to the machine outside the repository, which is outside every threat model boundary this repository defines (`03-threat-model/trust-boundaries.md` scopes the target as the invoking user's own filesystem). I record this as a documented, non-blocking observation rather than a new finding requiring remediation.

### Manifest (`lib/soft_foundry/manifest.rb`)
- `Manifest.load` refuses a symlink or non-regular file at `.ai/manifest.yml` before reading (guarded again upstream by `guard_path!` in `Installer#plan`, so this is defense in depth, not the only guard).
- `YAML.safe_load(..., aliases: false)` — no alias expansion (closes the amplification/billion-laughs class), and `safe_load` without `permitted_classes` restricts deserialization to basic scalar/collection types only (no arbitrary Ruby object instantiation), directly satisfying security.md's "protect against... insecure deserialization."
- `validate!` rejects any manifest path that is absolute, contains `..`, or is not under `.ai/` — this closes MIT-002 (`..` traversal in packaged names) for the *manifest's own entries*, independent of the packaged-source guard in `Installer::Source#entry_for` (which separately rejects `..` and symlinks in the packaged set itself). Two independent layers for the same class of threat (source-side and manifest-side) — good defense in depth, not redundant dead code.

### Dirty detection (`Git#dirty_paths`, `Installer#plan`)
- `dirty_paths` now passes `--ignored=matching`, so a `.gitignore`d-but-hand-edited managed file is treated as uncommitted (closes V3/ATTACK-021). I independently re-read the `git status --porcelain --untracked-files=all --ignored=matching` semantics: `--ignored=matching` reports files ignored via a *pattern* match (a `.gitignore` line), but git's documentation is explicit that it does **not** report files excluded only via `.git/info/exclude` or a repo-local `core.excludesFile` in the same "ignored" bucket in all git versions/configurations the way a tracked `.gitignore` line is. `08-attack`'s NEW-002 independently probed this exact question and found `.git/info/exclude`-only ignoring does *not* bypass the dirty-check (i.e., `git status --porcelain` still reports the file as untracked/modified through a different code path, not through the `--ignored` flag). I accept this finding because it was independently, live-reproduced with logged command output (`evidence/NEW-002-git-info-exclude-dirty-check.log`), which is the kind of primary evidence review can rely on rather than a restated claim.
- `@allow_non_git` no longer bypasses dirty detection when a real repository exists (`dirty = @git.repository? ? @git.dirty_paths : []`) — correct: `--allow-non-git` is meant for non-Git targets, and using it inside an actual repository should not weaken protection. Confirmed by code and by `06-verification`'s check 9 / `remediation-checks.log` cases (d) and (h) family.

### Root resolution (`CLI#resolve_root`)
- Refuses `/` explicitly, requires the target to be a directory, and — when `--root` is given explicitly — requires it to be the Git top-level via `File.realpath` comparison (defeats a symlinked `--root` argument that resolves to the same top-level through a different path string, and rejects one that resolves elsewhere). `GIT_DIR`/`GIT_WORK_TREE` are cleared in `Git#run` for every git invocation, closing THREAT-008's environment-redirection vector for `toplevel`, `dirty_paths`, and `ignored?` alike (I checked this is applied uniformly, not only for the `toplevel` call, by reading `Git#run`'s single implementation shared by every public method).
- Residual, disclosed and not reproduced live by attack (MIT-008): `--root /` under `--allow-non-git --dry-run` is not specially refused beyond the literal `/` string check (a `--root` that resolves to `/` via a symlink or relative path trickery might not be caught by the `candidate == "/"` string equality, since `candidate` is already `File.expand_path`'d but not `File.realpath`'d in the `--allow-non-git` branch, which returns `candidate` directly without a realpath call). I confirm this gap exists by reading `resolve_root`: the `File.realpath` comparison only happens in the `given && !allow_non_git` branch (`top = Git.new(candidate).toplevel; ... File.realpath(candidate) != File.realpath(top)`); the `allow_non_git` early return (`return candidate if allow_non_git`) skips realpath entirely, so a `--root` argument that is a symlink to `/` or to `$HOME` under `--allow-non-git` is not realpath-verified before use, only string-compared against the literal `/`. This is the same MIT-008 gap already disclosed in `09-remediation/summary.md` and carried in every subsequent phase; I independently confirm it is real and unresolved, not merely restated. See disposition below.

### CLI error classification and sanitization (`CLI#run`, `#sanitize`, `#upstream_guidance`)
- `sanitize` strips the gem root, the resolved root, the original `@root`, and `Dir.home` from diagnostic text (in that order — home last, matching the general-to-specific replacement order needed since `@resolved_root`/`@root` are typically inside `Dir.home` and must be replaced first or the home substitution would leave a stray home-relative fragment). I verified this ordering is correct: if `home` were substituted before `@resolved_root`, a `@resolved_root` value like `/Users/x/repo` would already have its `/Users/x` prefix replaced with `~`, breaking the subsequent literal-string match for `@resolved_root` itself — the code's actual order (root/gem-root first, home last) avoids this bug. Then strips all non-printable/non-ASCII bytes (`[^ -~]`). This satisfies errors.md's "preserve useful diagnostic context without exposing secrets or sensitive data" and the specific THREAT-012 concern (diagnostic leakage of absolute paths/hostnames).
- `Provider.sanitize` bounds length (200 chars) and strips non-printable ASCII from provider-controlled strings (model ids, error messages) before they are ever written to `runtime.yml` or printed by `models`; sanitization happens inside `Provider#discover` itself (not only at the print boundary), so the persisted `runtime.yml` is already clean — a second read of stale runtime state by `models` re-sanitizes defensively too. This is correct handling of untrusted external input at a trust boundary (security.md: "validate externally controlled input at trust boundaries").
- Exit-code classification (`InternalError`→4, `TargetError`/other `StandardError`→1) is a deliberate, single-point classification, not scattered `rescue`s; every `rescue StandardError` in the codebase (`cli.rb:57,88,111,150`; `provider.rb:35`) has explicit handling that converts the exception into a typed result or a classified exit code — none discards an exception silently, satisfying ruby.md's "do not broadly rescue StandardError without an explicit handling, reporting, and recovery strategy."

## Adjudication of the two unresolved attack findings

### ATTACK-F-N01 (medium) — `repository.yml` can redirect APP/TESTS/INFRA to nothing when the target has no files under the corresponding defaults
**Independent assessment:** confirmed by reading `Check#check_path_groups`: the redirect-detection rule is `@plane.files_matching(globs).empty? && !@plane.files_matching(defaults).empty?` — both sides must be evaluated, and if the *default* glob also matches nothing (a fresh or non-conventionally-laid-out repository), the comparison can never fire regardless of what the override says. I confirm this is real and reproduces THREAT-010's blinding goal for APP/TESTS/INFRA specifically. I also confirm, independently, that `CONTROL_PLANE`/`HARNESS_EVALS` are protected *unconditionally* (`PROTECTED_GROUPS` short-circuits before the empty/default comparison is ever reached — see `check_path_groups`'s `if ControlPlane::PROTECTED_GROUPS.include?(g) ... next`), so the eval-denial and control-plane-redirection half of the original V4 threat is fully closed regardless of this gap.

**Disposition: acceptable residual risk, not blocking.**
- The exploit precondition is narrow and requires the repository's own maintainer (or someone with commit access) to have already placed a redirect-to-nothing override in `repository.yml` *before* the first `init`/`check` run — this is a self-inflicted governance gap, not a remotely exploitable vector, and the same actor with that level of access already controls the repository's actual code and CI.
- The two highest-impact groups (`CONTROL_PLANE`, `HARNESS_EVALS` — the ones that would let an override silence eval denial or redirect policy files) remain protected unconditionally regardless of this gap.
- The consequence of the gap (reduced staleness/permission-drift detection for APP/TESTS/INFRA in a narrow repository shape) is a detection-quality regression, not a data-loss, credential-exposure, or write-outside-root vector.
- It is disclosed, reproducible, and narrowly scoped enough to fix without touching the security-critical write path (`SafeWrite`, `guard_path!`) that this change's threat model actually centers on.

**Recommendation carried to `consolidated.md`/learning (non-blocking):** tighten `check_path_groups` so an override matching zero files is flagged regardless of whether the corresponding default also matches zero files, i.e. drop the `!@plane.files_matching(defaults).empty?` condition, or additionally flag an all-three-groups-simultaneously-empty override as suspicious on its own. This is a small, low-risk follow-up; it does not require reopening the `SafeWrite`/`guard_path!`/dirty-detection work this change principally hardened.

### ATTACK-F-N02 (low, functional not security) — clean-install classification is now strict enough that a genuine Soft Foundry defect on a non-empty target is misreported as target-side
**Independent assessment:** confirmed by reading `Installer#plan`'s `clean` computation: `actions.none? { conflict/updated/forced } && actions.any? { repository.yml created } && extra_files.empty?`. Because `adapter_actions` (`.gitignore`, `AGENTS.md`, `CLAUDE.md`) is included in `actions`, any repository that already has an ordinary `.gitignore` or `AGENTS.md` before its first `init` — the common case for adopting Soft Foundry into an existing repository — produces an `updated` action for that file alone, making `clean` false regardless of whether every `.ai/` file installed with zero conflicts. This routes a genuine internal Soft Foundry defect surfaced by the post-install check to the target-side branch (`check: failed, resolve the conflicts above and rerun`, exit 0) instead of `InternalError`/exit 4 with upstream guidance.

**Disposition: acceptable residual risk, not blocking, and correctly self-rated as functional rather than security.**
- This is a strict overcorrection of the V5 fix (`ATTACK-015`, misclassification-as-internal-defect / diagnostic leakage): it can only ever cause a *true* Soft-Foundry-side defect to be under-reported as target-side; it cannot cause a false accusation that the *user's* repository is broken when the fault is actually Soft Foundry's, nor can it leak any diagnostic. The asymmetry matters: the original V5 violation (misclassifying ordinary target-side conditions as upstream defects, potentially leaking absolute paths) was the security-relevant direction; this residual is the safe direction of the same axis.
- The practical impact is a worse upstream bug-report experience (REQ-011's intent is diluted for the common "adopting into an existing repo" case), not a security or data-integrity issue.
- It is independently reproducible and already has a clear, narrow fix path (scope `clean` to `.ai/`-kind actions only, i.e. `actions.select { |a| a.kind == :ai }.none? { conflict/updated/forced }`, rather than the entire plan) that a future change can make without touching the hardened write-safety code.

**Recommendation carried to `consolidated.md`/learning (non-blocking):** narrow `plan.clean`'s scope to `.ai/`-kind actions (and the `.ai/repository.yml` creation check), excluding `.gitignore`/`AGENTS.md`/`CLAUDE.md` adapter actions, so a repository with ordinary pre-existing scaffolding can still route a genuine internal defect to exit 4.
