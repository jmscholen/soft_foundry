## Authorization envelope
- target: `soft-foundry init` and related commands from this repository at HEAD, exercised only against scratch copies and throwaway git repositories you create under a temporary directory (`mktemp -d`); the packaged source may be a copied, deliberately tampered copy of this repository under that temp directory.
- environment: local, ephemeral, synthetic data only.
- authorized_by: the repository maintainer, who instructed the lifecycle to continue; local ephemeral testing with synthetic data needs no further authorization under .ai/policies/human-boundaries.yml.
- allowed_surfaces: the CLI (init, onboard, check, gate, doctor, ci, models), filesystem manipulation inside the scratch directories (symlinks, FIFOs, hand-edited manifests, forged markers, .gitignore negations, permission changes, disk-quota simulation via injected failures only if achievable without system changes), environment variables for the CLI process (GIT_DIR, GIT_WORK_TREE, provider keys set to fake values), concurrent invocations, oversized or malformed inputs, and tampered packaged copies.
- prohibited_surfaces: this repository's working tree except changes/init-command/08-attack/; any path under the user's home directory outside the temp directory; any other repository; any network destination (unset OPENAI_API_KEY, ANTHROPIC_API_KEY, XAI_API_KEY, or use --no-onboard, so no provider call is made; if a test needs a "configured" provider use a fake key and expect a network error or block it); any third-party system; system configuration; anything requiring elevated privileges.
- data_constraints: synthetic only; never place real credentials in scratch files; scan your evidence for the string patterns of real keys before finishing.
- network_constraints: none permitted.
- destructive_actions: permitted only inside the scratch directories; delete them when done.

## Violations found

### V1 (ATTACK-004, THREAT-001, critical): out-of-root write through the atomic-write temp sibling
`Installer#atomic_write` writes to the predictable path `<destination>.soft-foundry-tmp` with `File.binwrite`, which follows symlinks, then renames it over the destination. `guard_path!` checks only the destination's components. A contributor commits `.ai/workflow.yml.soft-foundry-tmp -> /victim`, `AGENTS.md.soft-foundry-tmp -> /victim2`, and a dangling `.ai/manifest.yml.soft-foundry-tmp -> /new`. On `init --no-onboard`: exit 0, `check: ok`, `summary: created 171`; `/victim` is now byte-identical to canonical `.ai/workflow.yml`, `/victim2` holds the generated `AGENTS.md`, `/new` was created with the 18027-byte manifest, and inside the target `.ai/workflow.yml`, `AGENTS.md`, and `.ai/manifest.yml` are symlinks to the outside files. The next init refuses (`.ai/manifest.yml is a symlink`). Reproduction: `mkdir .ai; ln -s /path/to/victim .ai/workflow.yml.soft-foundry-tmp; soft-foundry init --no-onboard`. Every managed path (171 files plus the manifest, `.gitignore`, `AGENTS.md`, `CLAUDE.md`) is reachable; the attacker chooses the destination but not the content, which is enough to truncate or replace any file the maintainer can write (shell rc files, `authorized_keys`, CI config). Symlinks are committable, so the vector is PR-reachable; init reports success.

### V2 (ATTACK-005, THREAT-001, major): `.soft-foundry/` writes are unguarded
`Installer#with_lock` (`mkdir_p` + `File.open(RDWR|CREAT)`) and `Onboarding#write_runtime` (`File.write`) follow symlinks and hardlinks. With a committed `.soft-foundry -> /outside/dir`, `init` (no keys, no network) creates `init.lock` and `runtime.yml` in `/outside/dir`; with `.soft-foundry/runtime.yml -> /outside/victim` the victim is truncated and replaced by the YAML inventory, also through plain `onboard` and through a hardlink; a dangling `init.lock` link creates the outside file. The `.soft-foundry/` gitignore pattern matches only directories, so the symlink itself is not ignored (`git check-ignore` fails) and would be committed by `git add -A`. ATTACK-014c shows the in-root variant: `.soft-foundry -> state` leaves `state/runtime.yml` untracked and unignored.

### V3 (ATTACK-021, THREAT-004 and THREAT-006, major): the uncommitted-edit protection has two bypasses and the report promises otherwise
`Git#dirty_paths` uses `git status --porcelain --untracked-files=all`, which omits ignored files. With `.ai/rules/` in `.gitignore` (a one-line PR), a maintainer's uncommitted edit to `.ai/rules/general.md` is invisible: `init` reports `conflict (differs from manifest hash)` with `next: ... (uncommitted edits are never overwritten)`, then `init --force` reports `forced` and the edit is gone with no git recovery (`git checkout` fails: path not known to git). With the manifest additionally forged to the edited hash, a newer package overwrites it as `updated` without `--force`. Separately, `--allow-non-git` inside a git work tree sets `dirty = []`, so a forged-manifest, uncommitted edit is overwritten as `updated` with exit 0. Reproduction: `echo '.ai/rules/' >> .gitignore; git commit -am ignore; soft-foundry init --no-onboard; echo HARDENED >> .ai/rules/general.md; soft-foundry init --no-onboard --force`.

### V4 (ATTACK-013, THREAT-010, major): redirected path-group overrides silently neutralize staleness and eval denial
`check` errors only when an override empties a required group. A pre-seeded `.ai/repository.yml` with `paths: {APP: [nothing/**], TESTS: [nothing/**], INFRA: [nothing/**], HARNESS_EVALS: [nothing/**]}` is `skipped` by `init` (user-owned by rule), `init` exits 0 with `check: ok`, and `soft-foundry check` passes. Afterwards `lib/app.rb` no longer counts as code, `.ai/harness-evals/x.yml` is no longer covered by any skill's `deny_read`, and `gate verify` stays `PASS: evidence current` after editing `lib/app.rb`, whereas a control repository reports `STALE: code changed since ...: lib/app.rb`. The emptied variant is caught by `check` but surfaces as V5.

### V5 (ATTACK-015 with ATTACK-006, 009, 013, THREAT-012, major): target-side conditions are labelled "a defect in Soft Foundry", and one diagnostic leaks the target's absolute path
`CLI#init` converts any non-`SoftFoundry::Error` exception into `InternalError` (exit 4) with the text "This is a defect in Soft Foundry 0.2.0, not in your repository. Nothing further was changed." and instructions to fork and file upstream. Observed for: a regular file at `.soft-foundry` (`Errno::EEXIST`); `.soft-foundry` not writable (`Errno::EACCES`, which the specification classifies as target-side exit 1); a directory at `.soft-foundry/runtime.yml`, hit after a complete install with `check: ok` and the manifest written, so "Nothing further was changed" is false; a directory at `.ai/manifest.yml` (`Errno::EISDIR`); invalid YAML in a user file `.ai/profiles/custom.yml` (`Psych::SyntaxError`, manifest already written); a FIFO at `.soft-foundry/init.lock` (`Errno::ENOTSUP`); emptied path groups in `repository.yml` (`control-plane check failed immediately after a clean install`, 167 files written); a nested-array `APP` override (`NoMethodError` in `Check#overlap?`). No key value appeared in any output or in `runtime.yml` (canary strings absent everywhere). Path leakage: `CLI#sanitize` rewrites the cwd (`@root`), the gem root, and `Dir.home`, not the resolved `--root`; with cwd elsewhere the message line reads `dir_s_mkdir - /private/.../t-c/.soft-foundry`. The `~` rewrite keys on the `HOME` variable, so under a CI wrapper or direnv that changes HOME, stdlib frames appear as `/Users/<name>/...` (observed under the simulation).

### V6 (ATTACK-006, THREAT-014, minor): FIFOs hang init
A FIFO at `.ai/manifest.yml` blocks forever in `Manifest.load` (`File.binread` runs before any type check); a FIFO at `.gitignore` blocks inside the `git status --porcelain` subprocess that `plan` runs before `guard_path!` (any git command on that repository hangs as well). The other six FIFO positions are refused promptly. FIFOs cannot be committed, so this needs local filesystem access; `doctor` and `check` do not hang.

### V7 (ATTACK-019, THREAT-015, minor): `models` re-emits raw provider strings
`Onboarding` sanitizes what it prints, but `runtime.yml` stores the raw `error` and id strings (YAML-escaped, untruncated: a 5000-character id was kept), and `soft-foundry models` prints them raw: three ESC bytes and a forged `conflicts: none` line at column 0 were emitted. MIT-015's 200-character truncation is not implemented. Executed offline with an in-process `Net::HTTP.start` stub; no network was used.

## Denied cases with gaps and residual risks confirmed
- ATTACK-008: a forged manifest reverts committed hardening as `updated` (design-accepted); `git checkout` restores it; no `git diff` hint is printed (VER-006). Uncommitted hardening stays `conflict` even under `--force`.
- ATTACK-011: `--root / --allow-non-git --dry-run` is accepted (`root: /`, 171 planned creates); a HOME root prints no warning. MIT-008 asked for both. `--root` into a parent repository that contains the nested repo installs into the parent when given explicitly (root printed).
- ATTACK-012: a verbatim block inside a code fence or an HTML comment is `skipped` (the text remains readable; HTML comments do not nest); a verbatim block at byte 0, with CRLF endings, or without a trailing newline is reported `conflict` (false conflict, idempotence quirk); prompt-injection prose is preserved and reported `updated`, by requirement.
- ATTACK-014: when `.soft-foundry/` is ignored only by `.git/info/exclude` or a repo-local `core.excludesFile`, `.gitignore` is `skipped` and REQ-002's entry is not added on that machine; a fresh clone adds it on its first `onboard`/`init`.
- ATTACK-018: no hang at 512 MiB, but peak RSS is about twice the largest file (1.09 GB for an identical 512 MiB file, 827 MB for a 256 MiB `AGENTS.md`); MIT-014's streaming hash and 8 MiB pointer-file cap are not implemented; ATTACK-009 shows a 26 MB manifest parsed completely (5.4 s, 310 MB) before validation, with no byte or entry cap.
- ATTACK-003: a `docs` symlink refuses the whole run although `docs/user/README.md` would only be skipped.
- ATTACK-016: after `kill -9` one `<path>.soft-foundry-tmp` file remains until the next run overwrites and renames it; no truncated managed file, no manifest, no half-appended block. Two earlier attempts recorded in the same log are marked INVALID (the harness killed the `env` wrapper, not Ruby; the lock refusal seen there was correct behaviour against a live process).
- ATTACK-020: tampered package content installs faithfully (unpreventable); the next untampered init reports `.ai/README.md updated` and `AGENTS.md conflict`; attacker prose in `AGENTS.md` persists until a human resolves the conflict.
