## New findings from this pass

### ATTACK-F-N01 (medium) — `repository.yml` redirect-to-nowhere for APP/TESTS/INFRA is undetected in a repository with no files under any default path-group glob
`Check#check_path_groups`'s new redirect-detection rule is: flag an override as suspicious only if the override matches zero files *while the untouched default glob matches at least one file*. In a target repository that has no files under any of `paths.yml`'s default APP/TESTS/INFRA globs (`app/**`, `lib/**`, `config/**`, `db/**`, `exe/**`, `spec/**`, `test/**`, `infra/**`) — which describes any genuinely fresh repository before code exists, and any repository whose real application code lives under a different top-level convention — the default *also* matches zero files, so the comparison can never trigger. A `repository.yml` committed before the maintainer's first `init` with `paths: {APP: [nothing/**], TESTS: [nothing/**], INFRA: [nothing/**]}` passes both `init` and `check` completely silently (`check: ok`, exit 0) in that shape of repository, reproducing THREAT-010's original blinding goal (no staleness detection, though CONTROL_PLANE and HARNESS_EVALS remain unconditionally protected regardless of this gap — the eval-denial and control-plane-redirect half of the original violation is fully closed). Verified: the same override in a repository that already has `lib/app.rb` is correctly flagged; only the code-free/non-conventional-layout case is silent. Reproduction: commit the override above before ever running `init` in an empty repository; run `init`, then `check`; observe `check: ok`.

### ATTACK-F-N02 (minor, functional not security) — the auto-detected "clean install" exit-4 classification path is effectively unreachable outside an empty target directory
`Installer#plan.clean` requires no action across the *entire* plan (including `.gitignore`, `AGENTS.md`, `CLAUDE.md`, not just `.ai/` actions) to be `conflict`/`updated`/`forced`. Any repository that already has an ordinary `.gitignore` or `AGENTS.md` before its first `init` — which is the common case for a repository adopting Soft Foundry after already existing — gets an `updated` action for that file, making `clean` false. Consequence: a genuine Soft Foundry-side defect surfaced by the post-install check on such a repository is reported as an ordinary `check: failed, resolve the conflicts above and rerun` (exit 0, looking like the maintainer's problem) rather than exit 4 with upstream-fork guidance, even though every `.ai/` file installed cleanly and none is in conflict. This is a strict overcorrection of the V5 fix (it cannot cause a false accusation of Soft Foundry, only a missed true one) and is not attacker-controlled or security-relevant, but works against REQ-011's intent that genuine Soft Foundry-side failures be classified and surfaced as such. Reproduction: `git init`; `echo '*.log' > .gitignore`; commit; run `init` against a target with a reproducible internal defect (e.g. a corrupted packaged file that only fails `check`, not `plan`) and observe the failure is reported target-side rather than upstream-guided, even with zero `.ai/` conflicts.
