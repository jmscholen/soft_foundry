## Intent being proven
`soft-foundry init` installs the Soft Foundry control plane into an existing Git repository safely on the first run, idempotently on every later run, and without destroying user-owned content. From the user's side that means: a first-time maintainer gets a working control plane, a clean `check`, and a manifest in one command; a maintainer with existing `AGENTS.md`/`CLAUDE.md`/`.gitignore`/`docs/` keeps everything they wrote; an upgrade never silently overwrites a maintainer's edit (committed edits are `conflict` until `--force`, uncommitted edits are `conflict` even with `--force`); a maintainer who hand-copied `.ai/` earlier is adopted without loss; an agent can script on exit codes 0/1/3/4 and parse the status words; and when Soft Foundry itself is broken the user is told so, is sent upstream, and nothing is written.

Verification (`06-verification`, commit 6df4d15) already proved the deterministic gates: 67 tests, `ruby -wc`, `check`, `ci`, gem packaging (AC-017), and one end-to-end install. This phase does not repeat those. It runs the command the way each persona would and judges the observable result: the terminal report, the exit code, and the state of the target repository afterwards. It also exercises paths verification left without end-to-end evidence: the `updated` upgrade status for an owned `.ai/` file (VER-001), pointer files with prior content (AC-004/AC-005), the hand-copied tree (AC-008), `.gitignore` already effective (AC-009), `docs/` without `docs/user/` (AC-011), the broken package (AC-013), the symlinked `.ai` (AC-014), onboarding with no keys (AC-015), and non-ASCII stripping across every status word (AC-016).

The only implementation commit between the verification SHA and this HEAD is `6a41afd Complete verification for init-command`, which touched no file under `lib/`, `exe/`, or `test/`; the code evaluated here is the code verification tested.

## UI walkthrough evidence
`soft-foundry init` has no graphical or browser UI. Its user interface is the terminal report and the exit code, so the equivalent of a screenshot at each state transition is the captured transcript: the exact command, the complete stdout and stderr, the exit code, and the post-state of the target (`git status --porcelain`, `ls`, `cat`, `shasum`). Every transcript under `evidence/` is that walkthrough, taken at each meaningful transition (before the run, after the run, after commit, after the re-run, after `--force`). The scripts that produced them are under `evidence/scripts/` so the walkthrough can be replayed byte for byte. Evidence hashes are in `evidence/manifest.yml`.

The report was also evaluated as a product (see `results.md`, "Report usability"): whether each status word explains itself, whether the reason in parentheses tells the maintainer what to do, whether the `summary:` line supports a decision, and whether the resolved root is printed before anything is written.

## Accessibility interaction
Keyboard-only interaction is not applicable: the command is non-interactive, reads nothing from the terminal, prompts for nothing, and never waits for input (confirmed in every transcript, including the conflict, refusal, and internal-failure paths, all of which returned without input). There is no focus order or error-focus behaviour to test.

Screen-reader and low-vision readability was evaluated instead, since the report is the entire UI:
- Every outcome is conveyed by a word (`created`, `updated`, `skipped`, `conflict`, `forced`, `not configured`, `check: ok`), never by colour or a symbol. EVAL-011 captured raw bytes of three runs covering all five statuses and found zero non-ASCII bytes; after `tr -cd` stripping, every status was still identifiable by its first word and the parsed counts matched the summary.
- No ANSI escape sequences are emitted, so `NO_COLOR` is honoured trivially and the output reads the same in a pipe, a log file, or a screen reader.
- Output is line-oriented: one file per line, status first, then path, then an optional reason in parentheses. `summary:` and `check:` are single lines with fixed prefixes that can be jumped to.
- Errors are a single line prefixed `soft-foundry:` on stderr, with the resolving flag named in the same sentence (`pass --allow-non-git to install anyway`).
- Observed limitations are recorded as findings, not failures: a 171-line first-run report must be read to the end before the summary appears, and conflict lines are not grouped or repeated in the summary, so a screen-reader user locates a single conflict among 170 `skipped` lines only by searching for the word.
