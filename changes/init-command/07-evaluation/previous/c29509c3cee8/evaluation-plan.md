## Intent being proven
`soft-foundry init` installs the Soft Foundry control plane into an existing Git repository safely on the first run, idempotently on every later run, and without destroying user-owned content. From the user's side: a first-time maintainer gets a working control plane, a clean `check`, and a manifest in one command; a maintainer with existing `AGENTS.md`/`CLAUDE.md`/`.gitignore`/`docs/` keeps everything they wrote; an upgrade never silently overwrites a maintainer's edit (committed edits are `conflict` until `--force`, uncommitted edits are `conflict` even with `--force`) and now tells the maintainer which paths conflicted and what to do next; a maintainer who hand-copied `.ai/` earlier is adopted without loss; an agent can script on exit codes 0/1/3/4 (a malformed invocation is now exit 1, never 4) and parse the status words; onboarding names the variable to set when a provider is not configured; and when Soft Foundry itself is broken the user is told so, is sent upstream, and nothing is written.

Verification already proved the deterministic gates at this commit. This phase does not repeat them; it runs the command the way each persona would and judges the terminal report, the exit code, and the state of the target afterwards.

## UI walkthrough evidence
`soft-foundry init` has no graphical or browser UI; its interface is the terminal report and the exit code. The equivalent of a screenshot at each state transition is the captured transcript: exact command, complete stdout and stderr, exit code, and the target's post-state. Every transcript under `evidence/` is that walkthrough, taken before the run, after the run, after commit, after the re-run, and after `--force`. The scripts under `evidence/scripts/` replay it. Hashes are in `evidence/manifest.yml`; the previous run's transcripts remain under `previous/6a41afd123ca/evidence/` for comparison.

The report was again evaluated as a product (see `results.md`, "Report usability"), with attention to the three remediated behaviours: the usage-error classification, the `conflicts:`/`next:` guidance, and the environment-variable naming.

## Accessibility interaction
Keyboard-only interaction is not applicable: the command is non-interactive, reads nothing from the terminal, prompts for nothing, and never waits for input; every transcript, including refusals, conflicts, dry runs, and the internal failure, returned without input. There is no focus order or error-focus behaviour to test.

Screen-reader and low-vision readability was evaluated instead:
- Every outcome is a word (`created`, `updated`, `skipped`, `conflict`, `forced`, `not configured (set OPENAI_API_KEY)`, `check: ok`), never colour or a symbol. EVAL-011 found zero non-ASCII bytes across three runs covering all five statuses plus the new guidance lines; after stripping, every status and the `conflicts:`/`next:` prefixes remained identifiable.
- No ANSI escapes are emitted, so `NO_COLOR` is honoured trivially.
- Output is line-oriented with fixed prefixes (`root:`, `mode:`, `check:`, `summary:`, `conflicts:`, `next:`, `warning:`, `soft-foundry:` on stderr) that can be jumped to; the conflicted paths are now repeated in one line after the summary, so a screen-reader user no longer has to search 170 `skipped` lines for a single `conflict`.
- Remaining observations are recorded as findings: the `next:` line is a single 150-character sentence, and `check: ok` still immediately precedes an exit-3 summary.
