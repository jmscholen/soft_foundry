# Mitigations

| ID | Threats | Mitigation | Where enforced | Verified by |
| --- | --- | --- | --- | --- |
| MIT-001 | THREAT-001 | The guard protects its own configuration in every skill: a write tool naming, or a shell command mentioning, `.ai/policies/enforcement.yml`, `.soft-foundry/enforcement.yml`, `.claude/settings.json`, `.claude/settings.local.json`, or `.codex/hooks.json` is a violation whatever the skill's sets say. The environment variable cannot be set from inside a tool call (a `Bash` command's environment ends with the command), and is documented as the maintainer's. | `Guard#decide` (`SELF_PROTECTED`) | ATTACK-001; `test/guard_test.rb` |
| MIT-002 | THREAT-002 | Every path a case writes is checked before anything is written: relative, no `..` segment, no leading `/`, and it resolves under the scratch repository; a case that fails the check is reported `error` and nothing is written. Case files are inside `.ai/`, so `check` scans them for instruction-override phrases, secret shapes, invisible text, and fetch-and-execute commands like any control-plane file. Live sessions read the planted files as data: the phase prompt is `PhaseRunner#prompt`, unchanged, which names the skill contract and nothing from the case. | `HarnessEval::Case#validate`, `ContentScan.control_plane_paths` | ATTACK-002; `test/harness_eval_test.rb`, `test/check_test.rb` |
| MIT-003 | THREAT-003 | `.ai/harness-evals/**` stays in every skill's `deny_read` (lint) and in the protected write set (lint); the guard refuses `Read`, `Edit`, `Write`, and a `Bash` command naming it; `eval` prints ids, descriptions, and outcomes, never case content. | `Check#check_permissions`, `Guard#decide`, `CLI#eval` | ATTACK-003; `test/application_repo_test.rb` |
| MIT-004 | THREAT-004 | `judge` and `review` are never waivable, by code and by lint; the waivable set is read from `waivable_by_risk` for the risk exactly as declared (lower-cased, stripped), and a risk that is unset, a placeholder, or unknown waives nothing but optional phases; `change close` refuses without a completed judgment unless `--force`, and the first-phase gate check fails the record until the waiver is removed. The rationale text is still not judged (structure only, as every gate check). | `Gate#waivers_check`, `Check#check_waivers`, `CLI#change_close` | ATTACK-004; `test/factory_readiness_test.rb` |
| MIT-005 | THREAT-005 | Re-stamping the specify handoff moves the lock, but every commit-bound phase's `evidence current` check compares `02-specification/` against that phase's own `commit_sha`, so evidence produced before the edit is stale and must be redone; the lock check's failure text says so. | `Gate#staleness_check`, `Gate#specification_lock_check` | ATTACK-005; `test/factory_readiness_test.rb` |
| MIT-006 | THREAT-006 | Each case runs inside `Dir.mktmpdir` with an `ensure` that removes it, exceptions included; a case's exception is reported as `error` and the run continues; live cases run only with `--live`, one at a time, filtered by `--case`; a case may write at most 200 files. | `HarnessEval::Runner#run_case` | ATTACK-006; `test/harness_eval_test.rb` |
| MIT-007 | THREAT-007 | The shipped secret case uses a canary shape marked `soft-foundry:scan-allow` on its own line in the case file; the scratch record it plants is deleted with the scratch repository; `eval` output names the case and the check, never the planted text; this record's evidence quotes the eval output, not the case. | case file, `HarnessEval::Runner`, `ContentScan` | ATTACK-007; `test/content_scan_test.rb` (existing), the evaluation transcript |
