# Remediation

## Finding references
- **REM-001, from 06-verification (notes and results.md) and from the orchestrating session.** With the guard in block mode (REQ-FR-004), the fresh-context verification session could not run the test suite or the tool from the shell: the guard refused every shell command naming `exe/` or `test/`, because the verification skill lists `${APP}` and `${TESTS}` in `deny_write` and a shell command was checked against the deny sets by name alone. The session worked round it with a script outside the repository. The orchestrating session then hit the same refusal trying to launch `phase run evaluate` (naming `exe/soft-foundry`) and even to `cat` a skill's `permissions.yml` (naming `.ai/`), and found a second limit: `phase run` refused to rerun a complete phase even after its evidence had gone stale, so a remediation could not be re-verified without editing the verification handoff, which the remediation skill may not touch. In warn mode nobody had noticed either; block mode made both visible on the first run.

## Root cause
- The shell rule conflated "may not write" with "may not name". An evidence skill reads `${APP}`, `${TESTS}`, and `${CONTROL_PLANE}` by permission, and running tests, the tool, or `git diff` over them is reading, not writing; refusing the names made every evidence phase impossible to perform under block mode without going round the guard, which is the opposite of what block mode is for.
- `PhaseRunner#refusal` treated `complete` as final, although the gate already knows when a complete phase is stale.

## Changes made
- RED `d5940c2`: `GuardShellNamingTest` (verification may name `test/`, `exe/`, and `.ai/rules/` in a shell command; may not name harness evals, `.ai/policies/`, or the guard's own configuration; implementation may name the rules it reads and not `.ai/policies/`; a stale complete phase is not refused by `phase run`).
- GREEN (the commit this handoff names): `Guard#decide_by_skill`, shell branch: a command is refused when it names the guard's own configuration, protected policy or harness material (`.ai/policies/skill-permissions.yml` `protected:`), a `deny_read` path, or a `deny_write` path the skill may not read; a `deny_write` path the skill may read is allowed. `PhaseRunner#refusal` allows a complete phase whose gate reports `evidence current` failing. `test/guard_test.rb`: the `rm -rf .ai/policies` expectation reads the new reason.
- Requirement effect: REQ-FR-004 is unchanged (block is the default; the override order is unchanged; the guard still protects its configuration). The guard is narrower only in that naming a readable path from the shell is no longer a violation; a shell write to such a path is caught by the gate's staleness check and by review, as the guard's own limit (it cannot know what a command writes) always implied.

## Documentation owed, outside every skill's write set
The README paragraph that says the guard "refuses a command that names a denied path and passes everything else" and the comment at the top of `.ai/policies/enforcement.yml` saying the same must read: a shell command may name what the skill may read; it is refused when it names a path the skill may not read, a `deny_write` path the skill may not read, protected policy or harness material, or the guard's own configuration. This session cannot write `README.md` or `.ai/policies/` under the remediation skill, and in block mode it cannot create the machine-local override from inside the session (the guard refuses writes to its own configuration, as REQ-FR-004 requires). The maintainer applies these two text edits at merge, under the documented override on their own machine. Listed here so review and judgment carry it.

## REM-002 (from 08-attack, fresh claude session)
- **Findings.** ATK-F1 (major): the guard's self-protection was bypassed from the shell by `cd .soft-foundry && printf ... > enforcement.yml` (no token spells the file), by a variable-held directory or a command substitution, and through a `../` symlink in the write set that the write tool then edited; the attack downgraded the guard to warn in a scratch repository. ATK-F2 (major): `cat .ai/harness-*/cases/*` and `cd .ai && ls harness-evals` read the eval cases from an implementation session; only the full spelling was refused. ATK-F4 (minor, in part): a case file had no size cap.
- **Root cause.** `Guard#shell_paths` resolved only tokens that spelled a repository path in one piece: it did not follow `cd`, expand globs, or consider that a bare name after a `cd` is a path; `Guard#relative` never resolved symlinks, so a link in a skill's write set reached a file outside it.
- **Changes.** RED `bce5413` (`GuardIndirectionTest`: cd-relative names, globs, the `.soft-foundry` directory, symlinks through the write tool and the shell, the case size cap). GREEN (the commit this handoff names): `shell_paths` reads a command segment by segment (`&&`, `||`, `;`, `|`, newline), follows `cd`/`pushd` within the command, treats every bare token as a candidate path once inside a directory, and expands globs against the tree; `relative` resolves symlinks through the deepest existing ancestor (`realpath`) for every tool, so a link is judged by what it points at; everything under `.soft-foundry/` is the guard's own (shell mentions and write tools refused in every skill), not only the override file; `HarnessEval::MAX_FILE_BYTES` (64 KiB per case file) is linted.
- **Not fixed, accepted as residual (for judgment).** A path held in a shell variable or produced by a command substitution is still invisible to the guard: the shell check is a heuristic, as the policy says, and the backstops are the gate's staleness check (any write to code is caught), review of the diff, and the machine's own file permissions. ATK-F3 (self-attested `commit_sha`, re-stamped by hand) is the record's trust model: `AGENTS.md` forbids it, the git history shows it, review reads the history; the gate does not compare a handoff's `commit_sha` with the commit that wrote it, which a later change can add. The unquoted `mode: off` observation fails safe (the guard stays in block) and is noted for the README.
- **Documentation owed, outside every skill's write set (adds to the list above).** The README guard paragraph should also say: a shell command is read segment by segment with `cd` followed, globs expanded, and symlinks resolved; everything under `.soft-foundry/` is the guard's own; a variable or a command substitution can still hide a name, which is why the gate's staleness check and review back the guard; quote `mode: "off"` in the override.
- **Evidence invalidated.** Verification at `8ecce2f`, evaluation at `fcf79eb`, attack at `ba15a56`.
- **Required reruns.** Verification, evaluation, and attack at the remediated commit, each through `phase run`; ATTACK-001 and ATTACK-003 must now deny the cd, glob, and symlink routes.

## REM-003 (from the second 08-attack, fresh claude session)
- **Findings.** ATK-F5 (major): `cd lib && cd .. && cd .ai/policies && sed ...` was allowed, because `relative` returned the absolute root for the root itself, `shell_paths` dropped it, and the tracked directory stayed in `lib`; the first round's routes to the policy and the eval cases worked again through it. ATK-F6 (major): a `~nosuchuser` or `~+` token or a NUL byte made `Guard#relative` raise, the hook exited 1, and only exit 2 refuses: the guard failed open. ATK-F7 (minor, in part): brace expansion (`.ai/{policies,rules}/x`) was not followed; the Grep and Glob tools were not guarded at all.
- **Root cause.** `relative` had no representation for the root; the `cd` tracker could not express "left the root"; no exception handling existed on the decision path; the hook matcher predated the search tools.
- **Changes.** RED `78a1b35` (`GuardFailClosedTest`). GREEN (the commit this handoff names): `relative` returns `""` for the root; `shell_paths` tracks the directory as `""` (root), a relative path inside it, or `nil` once the command has left the root, after which only absolute paths are candidates; `GLOB` includes `{` and globs expand with `FNM_EXTGLOB`; `Guard#decide` rescues any exception into a violation that says the call could not be decided, and `CLI#guard` does the same around it, so block mode exits 2 and warn mode reports; `Grep` and `Glob` are guarded by their `path` (and a glob pattern's static prefix) against `deny_read`; `Hooks::GUARD_MATCHER` names them, so `hooks install --claude` wires them.
- **Not fixed, accepted as residual (for judgment).** A search or a recursive read from the root or any directory wider than a denied one (`Grep` with no path, `grep -r .`, `find -exec`) still reaches the denied material: the guard cannot filter results, and refusing every root-wide read would make the shell unusable; it is the documented limit, with the gate's staleness check and review behind it. Variables and command substitution likewise. The case size cap stays per file. SIGKILL cleanup of scratch repositories is unproven.
- **Documentation and installation owed, outside every skill's write set.** The README guard paragraph should say the matcher now includes Grep and Glob and that an existing repository reruns `soft-foundry hooks install --claude` (and `--codex`) to pick it up; this repository's own `.claude/settings.json` and `.codex/hooks.json` still carry the old matcher, which no skill may write.
- **Evidence invalidated.** Verification at `4749268`, evaluation at `98b336f`, attack at `fe9e40d`.
- **Required reruns.** Verification, evaluation, and attack at the remediated commit, each through `phase run`; ATTACK-001 and ATTACK-003 must deny the chained `cd ..` route, and the hook must refuse the unresolvable tokens.

## REM-004 (from the third 08-attack, fresh claude session)
- **Findings.** ATK-F8 (major): further spellings reached the guard's configuration and the eval cases after REM-003: quoted path segments in a `cd`, a `cd` out of the repository and back by a relative path, `CDPATH`, `find` with a wildcard name and `-exec`, a `?` glob in a `cd`, a symlink made and used in one command. ATK-F9 (minor): the Grep and Glob tools and `grep -r` from the root still reach the eval cases, because only the tool's path is checked. EVAL-F4 (minor): an undecidable refusal printed "the  skill's" with an empty skill name.
- **Root cause, and the decision.** A shell check that works by recognising path names in a command can always be spelled around; three rounds of hardening each closed the spellings found and the next round found more. The preventive check stays (it refuses the plain routes, which is most of them) but stops being the control that MIT-001 rests on. The control is now detective and corrective: the guard records the contents of its own configuration before every tool call and, after every shell command, restores any of them that changed during the call and refuses, however the change was spelled. The read side (eval cases through a root-wide search) has no corrective equivalent and is accepted as residual below.
- **Changes.** RED `7f4db33` (`GuardTamperTest`). GREEN (the commit this handoff names): `Guard::OWN_FILES` (policy, override, the three hook files), `Guard#record_baseline!` (PreToolUse, into `.soft-foundry/guard-baseline.yml`) and `Guard#check_after!` (restore to the baseline; with no baseline, the committed policy from git and the override removed; a `tamper` line in the guard log); `soft-foundry guard --after`, which restores first and reads the mode afterwards, since the change it undoes may be to the mode itself (exit 2 in block mode, a warning in warn mode); `hooks install --claude` writes the PostToolUse entry (matcher `Bash`) beside the PreToolUse one and `uninstall` removes both; an undecidable refusal says the guard refuses what it cannot decide. A change made between tool calls, in the maintainer's own shell, is the next baseline and stands.
- **Not fixed, accepted as residual (for judgment).** Reads: a root-wide search (`Grep` with no path, `grep -r .`, `find`) reaches the eval cases and anything else under `.ai/`; the guard cannot filter results, and refusing every wide read would make the shell unusable. A hostile session that reads the cases can tailor its work to them; the cases are also reviewed like any control-plane file, and a tailored implementation still faces a fresh-context review and attack. Writes to the guard's configuration by a spelling the preventive check misses are now undone after the call, not prevented; a command that both changes the configuration and acts under the changed mode within the same shell command gets that one command's worth of latitude. Codex has no PostToolUse entry installed (its hook contract for that event was not checked). The self-attested `commit_sha` (ATK-F3) stands as before. Beyond these, the complete answer is an OS sandbox, which the panel-phases judgment already recorded as out of scope for this repository.
- **Documentation and installation owed, outside every skill's write set.** The README guard section must describe the post-call check and that an existing repository reruns `soft-foundry hooks install --claude` to get it; this repository's own `.claude/settings.json` has no PostToolUse entry until the maintainer does.
- **Evidence invalidated.** Verification at `4330cf4`, evaluation at `9307b23`, attack at `aa54650`.
- **Required reruns.** Verification, evaluation, and attack at the remediated commit, each through `phase run`. The attack phase is asked to judge the detective control as a control (does a change made by any spelling get restored and refused after the call?) rather than to enumerate further spellings the preventive check misses, which this record already accepts as residual.
