# Implementation Decisions

| Decision | Alternatives considered | Reason | Consequence |
| --- | --- | --- | --- |
| Tracks share one phase list and one gate; a track only changes what precedes implementation, when the specification locks, and whether an exploring stage exists | A second workflow file per track; a shorter phase list for `iterative` | The hardening phases must be identical or the iterative track becomes a weaker lifecycle rather than a later-starting one; one gate means one set of semantics to document and test | Three new gate checks, a track-aware predecessor, and no change to staleness, commit binding, or judgment |
| The exploring stage is a status (`exploring`) with a stage skill, not a lifecycle phase | A new `explore` phase between plan and implement with its own handoff and completion gate | A phase completes by producing evidence bound to a commit; the stage explicitly produces none and ends by a person's act, which is a command, not a handoff | `current_phase` stays a lifecycle id (`implement`); `AGENTS.md` says which skill to load while exploring |
| `change vet` locks the specification at HEAD and requires intake and specification to be committed | Lock at the specification handoff's `commit_sha`; allow uncommitted spec at vet | The handoff's `commit_sha` predates the record commit, so it is not a commit the spec exists at; an uncommitted spec would read as changed on the very next gate run | Two refusal reasons name the uncommitted paths; the journal is deliberately not required to be committed |
| `vet_requires` is per track in `workflow.yml`, defaulting to intake and specify | Hard-code the two phases in the CLI | A repository that wants threat modelling before vet on every iterative change adds it in policy, not code | `check` verifies the phases exist |
| `reopen` resets handoffs from `implement` onward to `pending`, appends a note, keeps every file | Leave handoffs complete and let the gate fail; delete the phase directories | Leaving them fails `ci` on the next commit and forces a hand edit of evidence, which is what anti-fudging forbids; deleting loses observed results | The reopening is recorded in `metadata.yml` and in each reset handoff's `notes` |
| `track permitted` is reported on the first phase only | On every phase; a record-level check with new plumbing | It is a fact about the change, and the first phase is non-pending as soon as work starts, so `status`/`ci` show it once | One check, in one place; `vet` re-derives the same fact for its own refusal |
| A control plane without `tracks:` has an implicit `gated` track | Require the block; fail `check` without it | Installed control planes predate this change and must keep passing `check` and `ci` after a gem update | `ControlPlane#tracks` synthesises `gated`; a test removes the block and asserts nothing changes |
| `check` refuses a stage skill whose write set overlaps a commit-bound phase's directory | Trust `permissions.yml`; document the rule only | "Produces no evidence" is the invariant the whole design rests on; a lint makes it fail loudly if a future edit widens the write set | `check_exploring_writes`; `check_phase` refactored onto `check_skill_contract` so both kinds of skill are linted the same way |
| The stage skill may write `05-implementation/**` and `02-specification/**` | Confine it to `exploration/**` | Implementation's log and decisions are the natural place for what was built; the specification is a living draft during the stage by design; neither is commit-bound evidence | Both are still denied to the stage after vet by the ordinary phase skills' permissions taking over |
| The environment advisory treats NOT_APPLICABLE like PASS | Only PASS clears it | A library (this repository) has no deployable environment and says so with a rationale; advising it forever would be noise | The advisory names NOT_APPLICABLE as a valid answer |
| `--by` defaults to git `user.name` | Require `--by`; default to `$USER` | The git identity is what already signs the commit that follows; `$USER` is a machine account | `Git#user_name`; `$USER` remains the fallback when git has no identity |
| Risk forces the track; it does not yet select phases within a track | Full risk-tiered phase selection now | Forcing is the one rule the maintainer's request needed (a high risk feature does not get to skip the up-front phases); the rest is the roadmap's separate item | `forced_by_risk` in policy; the profile's finding says exactly this |
