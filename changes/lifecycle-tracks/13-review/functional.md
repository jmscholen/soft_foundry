## Findings
| ID | Severity | Location | Finding | Rule or requirement |
| --- | --- | --- | --- | --- |
| REV-001 | minor | `lib/soft_foundry/change_record.rb` `vet!`, `reopen!` (and the pre-existing `close!`) | Each rewrites `metadata.yml` with `YAML.dump`, which drops the template's explanatory comments. `close!` already did this, so every closed record in this repository is comment-free; now a vetted or reopened record is too. Cosmetic: the comments live in the template. A text-edit approach like `declare_surfaces!` would preserve them; follow-up. | REQ-TRK-004, REQ-TRK-007 |
| REV-002 | minor | `lib/soft_foundry/change_record.rb` `track` | A record with no `track:` key is read as the repository default. If a repository later flips `tracks.default` to `iterative`, its open records written before tracks existed would silently be read as iterative (discover, threat_model, and plan no longer required before implement). In this repository two open records lack the key (`init-command`, `upstream-failure-reporting`); both are on the default and the default is gated, so nothing changes today. Recommendation: pin `track: gated` on open legacy records before ever changing the default; follow-up. | REQ-TRK-001, REQ-TRK-012 |
| REV-003 | info | `lib/soft_foundry/gate.rb` `specification_lock_check` | Locks `02-specification/` only. `00-intake/` is also vet-required and committed at vet but not locked afterwards; intent may be reworded without a reopen. Consistent with the requirement (the specification is what hardening is checked against). | REQ-TRK-005 |
| REV-004 | info | `lib/soft_foundry/cli.rb` `change_vet` | The vetted commit is HEAD before the vet writes `metadata.yml`, so the commit holding `vetted:` is the one after; the lock is on the specification's commit, not the vet's own. Documented in the README example (vet, then commit). | REQ-TRK-004 |
| REV-005 | info | `lib/soft_foundry/cli.rb` `change_vet` | The journal is required non-empty but not committed at vet, by decision; a journal edited after vet is not a lock violation. Correct for a document that keeps growing across reopenings. | REQ-TRK-004 |
| REV-006 | info | `lib/soft_foundry/change_record.rb` `reopen!` | Resets only hardening phases whose status is not `pending`, so a fresh reopen prints "no hardening phase had started" rather than listing sixteen directories. EVAL-006 confirms the reset list is exactly the phases that had started. | REQ-TRK-007 |
