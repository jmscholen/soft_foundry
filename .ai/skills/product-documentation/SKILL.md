# Product Documentation
Convert successfully evaluated user behavior into accurate user instructions. Ground claims in passing EVAL journeys and their evidence; do not document behavior merely because code or a plan suggests it exists. Identify documentation invalidated by changed journeys.

Write bounded claims: say what the tool checks and under which conditions, and name known gaps, instead of absolutes such as "cannot", "never" or "always". "The guard checks calls made from the repository root; a shell that changes directory is not guarded" survives an attack; "cannot be reached from inside a guarded session" does not.
